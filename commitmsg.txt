Fix audio not following the window due to async device-change race

MMDevice.Selected is fire-and-forget: Windows applies the default-device
change asynchronously, with an observed lag of anywhere from a few
milliseconds to over a second. The old shortcut in SetDefaultPlaybackDevice
("already <name>") read a state that had not landed yet, so a new switch was
skipped, and the in-flight change then moved the audio to the monitor the
user had just left. That presents exactly like "the switching stopped
working", which is why it went undiagnosed.

Replace the one-shot check with a convergence loop: after every switch,
re-check the actual default device every 750ms and re-apply it on drift,
stopping only after it has held for two consecutive ticks. This converges
regardless of when Windows lands the change, or of an external tool
overriding it. The loop is lazily created and disposed as soon as it
converges, so an idle app holds no timer.

Verified with a deterministic simulation of Windows' async behaviour:
- focus A -> B -> A within one OS lag, stale change landing on the wrong
  device: loop corrects it and converges on the focused monitor
- external change after convergence: next focus event restores it
- 60s idle: zero re-applies, zero spurious switches, no resident timer
